# FateCore v0.3 Leakage Postmortem

## Summary

Round 2 v0.3 reached `R2_log(y_jcr_jif)=0.9525`, but production cold-start testing exposed worse behavior than v0.2-prod. EMPA-REG cold-start JIF dropped from the v0.2-prod baseline range to about `0.61`, so main rolled production back in commit `12bdfea`.

The failure was not internet/data volume. It was feature availability mismatch: the offline test set contained post-publication values that a new manuscript cannot have.

## Leaking Features

Direct post-publication/corpus-response features in v0.3:

- `icite_citation_count`
- `icite_nih_percentile`
- `icite_apt`
- `icite_cited_by_clin`
- `citations_openalex`
- `citations_s2`
- `citations_crossref`
- `fwci`
- `fwci_topic_norm`
- `reference_count`
- `has_pmcid`
- `pmc_body_word_count`
- `pmc_figure_count`
- `pmc_table_count`
- `pmc_ref_count`
- `epmc_body_word_count`
- `pdf_body_words`
- `unpaywall_is_oa`
- `unpaywall_journal_oa`
- `unpaywall_journal_doaj`
- `preprint_pub_gap_days`

Round3 also treats accepted-journal `j_hist_*` values as unsafe for true cold-start deployment, even though prior journal metrics are valid when a user explicitly supplies a target journal. In the training table, accepted journal history is known because the paper is already published; in a no-target cold-start forecast, it is not.

## Why R2 0.95 Was Fake

The v0.3 train/test split was random and honest with respect to rows, but not honest with respect to time-of-availability. Published test rows had citations, FWCI, iCite, PMCID, fulltext deposit, and OA indexing already populated. New production manuscripts have those fields missing.

LightGBM learned strong split paths on those populated post-publication features. At production cold-start, the same features became `NaN`, so the model followed missing-value default branches that were underrepresented for high-quality published papers. The model effectively learned "no citations/fulltext/iCite means low impact", which is correct for a published paper with no citations but wrong for an unpublished submission.

The top v0.3 JIF features confirmed the problem: `icite_citation_count`, `icite_nih_percentile`, `reference_count`, `pmc_body_word_count`, `citations_openalex`, `icite_cited_by_clin`, `epmc_body_word_count`, `pmc_ref_count`, `pmc_table_count`, and `pmc_figure_count` all appeared in the top 30.

## Round3 Correction

Round3 v0.3-prepub uses 34 cold-start-safe features:

- title/abstract shape
- article type flags
- author count and author h-index features
- affiliation/funding/NIH grant indicators
- preprint presence only
- Q-score aggregates computed from supplied manuscript text

It excludes all post-publication feature groups and accepted-journal historical metrics for the deploy candidate.

Result:

- `R2_log(y_jcr_jif)=0.4610`
- forbidden feature count: `0`
- suspicious high-R2 guardrail: passed
- EMPA-REG cold-start local smoke: stable versus v0.2-prod
- deploy decision: hold, because `0.4610 < 0.48`

## Future Leakage Filter Rule

For every future FateCore training run:

1. Every feature must be classified as `always_pre_submission`, `user_optional_pre_submission`, `target_journal_optional`, or `post_publication_forbidden`.
2. Production deploy models may use only `always_pre_submission` unless endpoint logic explicitly verifies that optional inputs are supplied.
3. Any model with `R2_log(y_jcr_jif) >= 0.70` must be treated as suspicious until a feature-availability audit proves otherwise.
4. Evaluation must include an EMPA-REG cold-start smoke with no target journal and no post-publication fields.
5. The eval report must list forbidden feature count and top-30 feature importance with forbidden flags.
6. A model can be pushed to production only if both offline deploy threshold and cold-start smoke pass.
